# 大任务 001：初版模块审阅参考清单

## 使用说明

这是审阅时的临时提示，不是需要逐项填写的新问卷，也不代表以下设计均已获得最终确认。可以只指出不认可或不清楚的地方；未提及不代表自动批准。

- 对照设计：`docs/design/01-初版设计.md`。
- 对照原型：`code/frontend/`。
- 审批写入：`01-主管/草稿.md`。
- 本文件只用于大任务 001，任务结束并提炼后清理。

## 一、先看整体结构

- [ ] “今天”是否适合作为默认首页？
- [ ] 今天、模块规划、阶段目标、日历、每日记录、文档库、财务、账密这 8 个入口是否清楚且必要？
- [ ] 模块、子模块、阶段目标、任务、记录、文档之间的关系是否符合你的使用方式？
- [ ] 从模块产生任务，到今天执行，再到晚间复盘，主流程是否连贯？
- [ ] 是否有一眼看上去多余、缺失或命名不准确的入口？
- [ ] 首版保留模拟数据的边界是否可以接受？

## 二、按页面抽查

### 01 今天

- [ ] 四象限分类和手动调整方式是否直观？
- [ ] 新建任务的默认字段是否足够轻量，“启动动作”是否容易理解和填写？
- [ ] 早间计划、晚间复盘、完成/延期/放弃是否符合实际节奏？
- [ ] 今日重点、负载提示和任务状态是否主次清楚？

### 02 模块规划

- [ ] 模块与子模块的增删改、暂停、归档和重新启用是否符合需要？
- [ ] 日常生活、健身、学习、开发、游戏的示例是否体现各自差异？
- [ ] 模块主页能否说明“为什么做、当前做什么、下一步是什么”？
- [ ] 模块生成任务和默认属性的方式是否有歧义？

### 03 阶段目标

- [ ] 一个模块突出一个主阶段目标，其他目标排队或暂停，是否符合预期？
- [ ] 开始结束时间、里程碑、完成标准和关联成果是否足够验收？
- [ ] 执行数据与真实效果是否区分清楚？
- [ ] 83 天可选模板和健身月度规划是否没有被误写成固定规则？

### 04 日历

- [ ] 日历是否清楚呈现计划任务与模块/目标来源？
- [ ] 新建、移动或调整计划日期的操作是否自然？
- [ ] 日历与四象限是否各自承担清晰职责，没有复制两套任务？

### 05 每日记录

- [ ] 记录与任务、模块、目标的关联是否符合使用习惯？
- [ ] 早晚记录、复盘和执行痕迹是否避免重复填写？
- [ ] 空状态和跳过复盘是否不会制造压力？

### 06 文档库

- [ ] 方法论、攻略、正确做法、错误记录和学习总结是否便于统一查找？
- [ ] 文档跨模块关联、任务只属一个模块的边界是否清楚？
- [ ] 版本更新、失效攻略或历史经验的处理是否需要补充？

### 07 财务

- [ ] 账户、流水、消费和总资产之间的关系是否易懂？
- [ ] 花呗、美团月付等既作为支付方式又作为还款对象时，统计口径是否清楚？
- [ ] 还款不重复计算支出的表达是否符合你的理解？
- [ ] 初始余额为 0、允许负数、手动记录的首版边界是否可接受？
- [ ] 还贷平台、还贷记录和基础统计是否有缺失或过度设计？

### 08 账密占位

- [ ] 首版仅保留入口和壳、不保存完整密码是否符合当前边界？
- [ ] 页面是否明确提示安全限制，没有让人误以为已经安全保存真实密码？
- [ ] 后续模块化替换空间是否足够，当前是否需要继续简化？

## 三、跨页面与视觉检查

- [ ] 三主题切换是否方便，默认“温暖生活风”是否符合要求？
- [ ] 桌面和窄屏下，导航、表格、表单、日历和四象限是否可用？
- [ ] 相同概念在不同页面的名称、状态和操作是否一致？
- [ ] 是否出现原型能点、但真实数据规则尚未定义的关键歧义？
- [ ] 哪些内容应明确留到下一版，而不是继续塞进初版？

## 四、定稿前最后检查

- [ ] 所有“不认可”都有处理结论，而不是只记录在待办里。
- [ ] 所有影响开发的“待定”都已解决，或明确后置且不会阻塞首版。
- [ ] 能区分“技术验证通过”和“用户确认设计”。
- [ ] 只有明确认可初版后，才进入员工正式开发交接。
