# 个人系统产品设计与开发流程

## 一、核心原则

设计者是项目的设计者、掌舵者和主管，负责项目开头并管理方向、草稿、spec、todo 和 SOP。功能与界面初版未经用户确认前，所有产品工作都属于设计者，包括原型代码。员工不参与反复设计讨论；用户确认后才通过正式 spec 交接。

设计完成不等于开发完成。原型可以使用 React 等真实技术栈和模拟数据，用于确认交互、目录和可实现性，但不得因此提前接后端或扩展未确认功能。

## 二、设计阶段标准流程

### 001 接收规格

**动作**：项目开头将原始想法写入 `01-主管/草稿.md`；设计者据此管理 spec、todo 和 SOP。工作流要求可连同已有 spec 逐字归档到 `01-主管/specs/`。

**产出**：目标、范围、限制和验收依据。草稿是当前工作输入，specs 是阶段归档，两者不长期重复保存。

**正确做法**：同时保存新要求与已有执行方案。**错误示例**：只保留助手总结，丢失用户原始约束。

### 002 内容边界

**动作**：从原始想法中确认核心场景、模块范围、首版重点和后置能力。

**产出**：初步模块清单、用户场景和暂缓范围。

### 003 同行调研

**动作**：围绕核心问题观察同行入口、任务组织、目标、记录和隐私处理。

**产出**：可复用参考进入 `ref/`；临时材料进入 `temp/`，提炼后清理。

**正确做法**：说明借鉴什么、放弃什么。**错误示例**：因同行存在功能就直接加入首版。

### 004 交互式详细设计

**动作**：每轮一个主题、通常一个问题、最多三个选项，根据回答动态调整下一题。

**产出**：原始问答和结构化结论。

**正确做法**：先原文后结论，保留问题修正。**错误示例**：一次发送长问卷、只保存摘要、把推荐项当用户选择。

### 005 风格与完整原型

**动作**：先用同内容 Demo 比较风格，再按用户决定完成可交互原型和目录结构。

**产出**：设计原型、模拟数据、技术结构和验证证据。

**正确做法**：三主题可共存时提供切换，不强迫单选。**错误示例**：用户尚未审阅就进入真实数据开发。

### 006 模块审阅

**动作**：第一轮审大方向，第二轮按需要审功能细节，逐轮修改并验证。

**产出**：`docs/design/02-…`、必要时 `03-…`，以及用户最终确认。

**门槛**：预期 1～2 轮，但核心分歧未解决不能交接。

### 007 正式开发交接

**动作**：主管形成根目录员工 spec；员工一次完整回访；主管最多修订一次；员工执行并验证。

**产出**：最终实现、执行记录、测试证据和遗留事项。

**后续**：员工从自己的历史中提炼经验，先更新自己的 Agent，再将待分配候选放入 000。

## 三、逐步记录要求

每一步都记录：执行动作、用户原文、设计结论、验证结果、正确做法、错误示例和待定项。

- 原话是证据，结构化结论是索引，两者不能相互替代。
- 验证通过不等于用户确认；技术验收和产品验收分别记录。
- 新结论覆盖旧结论时保留变化原因，避免后续误读。
- 无内容时不虚构经验，后端尤其如此。

## 四、阶段归档与知识分配

按以下顺序执行：

1. 员工的一次 spec 完成后，将当时主管草稿与根目录 spec 按顺序拼接到 `01-主管/specs/` 的同一个新编号文件；todo、设计记录和执行记录分别归档。
2. 将稳定职责和工作方式吸收到对应 Agent。
3. 将跨任务流程固化到正式 SOP。
4. 将未稳定、待分配或待验证内容放入 `000-候选池.md`。
5. 删除已被完整吸收的中间产物，重置主管草稿、根目录 spec/todo 和当前记录模板。
